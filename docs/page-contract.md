# Контракт листа: как отдавать готовый markdown в PTO

Документ для команды, которая делает распознавание. PTO хранит PDF, показывает
чертёж и текст рядом, ведёт правки инженеров и замечания. Ваш пайплайн отдаёт
готовый markdown листа — по одному листу за запрос.

## Запрос

```
PUT /api/documents/<documentId>/pages/<pageNumber>
Authorization: Bearer <PTO_INGEST_TOKEN>
Content-Type: application/json
```

Тело:

```json
{
  "markdown": "## Страница 14\n\n# Физико-механические характеристики грунтов\n\n| Тип грунта | ... |\n",
  "kind": "table",
  "source": "model",
  "warnings": [
    "OCR check: MD has >500% of OCR numbers (possible hallucination) — OCR=6 MD=106"
  ]
}
```

| Поле | Обязательное | Значения | Что делает |
| --- | --- | --- | --- |
| `markdown` | да | непустая строка | текст листа, попадает в интерфейс как есть |
| `kind` | нет | `drawing`, `table`, `text`, `mixed` | тип листа; влияет на фильтры и раскладку панели |
| `source` | нет | `model`, `heuristic` | по умолчанию `model`; показывается бейджем над текстом |
| `warnings` | нет | массив строк | Журналы → «Агент ИИ (ошибки)» — разбор сверки модели |

Ответ `200`:

```json
{ "ok": true, "pageNumber": 14, "readyPages": 14, "pageCount": 82 }
```

Коды ошибок: `401` — неверный токен, `404` — нет такого документа, `400` —
пустой markdown или неверный номер листа, `503` — на сервере не задан
`PTO_INGEST_TOKEN`.

Пример:

```bash
curl -X PUT "https://<host>/api/documents/$DOC/pages/14" \
  -H "Authorization: Bearer $PTO_INGEST_TOKEN" \
  -H "Content-Type: application/json" \
  --data @page-14.json
```

## Идемпотентность и правки инженера

Повторный `PUT` того же листа перезаписывает markdown. Если лист уже правил
инженер, предыдущая версия не теряется: она уходит в журнал правок листа с
автором «Пайплайн», и инженер видит, что текст пришёл заново.

Порядок листов не важен: лист с номером больше текущего `pageCount` увеличивает
счётчик листов документа.

## Формат листа

Опора — папка эталонов (`ИДЕАЛ_*.ref.md`). Устойчивая структура листа:

1. `## Страница N` — номер листа внутри исходного PDF.
2. Строка предупреждения об OCR в квадратных скобках, если проверка сработала.
   Лучше дублировать её в `warnings`: тогда инженер увидит значок сверки, а не
   текст в середине листа.
3. `# Заголовок листа` — название таблицы или чертежа.
4. Таблицы — GFM: строка заголовков, строка выравнивания, строки данных.
   Объединённые заголовки разворачиваются в плоские через тире:
   `Удельное сцепление С, кПа — Рекомендуемое`.
5. Блок `**Цветовая разметка:**` — список того, что в оригинале выделено цветом.
6. `---` и `## Штамп` — таблица штампа листа.
7. Служебные пометки — HTML-комментарии: `<!-- 1306 identical empty rows removed -->`.
8. **Привязка к чертежу (подсветка):** перед абзацем расшифровки — стабильный ID
   объекта DWG в HTML-комментарии. Тот же ID должен быть в CSV-геометрии листа
   (колонка `id` у строк `type=text`). Подробнее — раздел «Подсветка» ниже.

Разрешён inline-HTML для оформления: `<sub>`, `<sup>`, `<br>`, `<span>` и атрибут
`style`. Всё остальное вырезается на рендере (`rehype-sanitize`), скрипты и
обработчики событий не сработают. Не используйте `<script>`, `<iframe>`,
`javascript:`-ссылки — они просто исчезнут.

Комментарии `<!-- obj:… -->` в тексте **не отображаются** инженеру — они только
для связи с чертежом.

### Разделы листа: что сворачивается

Фронтенд режет лист по `##` (`splitMarkdownSections`) и по умолчанию сворачивает
служебные разделы — отладку конвейера, которая иначе занимает первый экран, а
полезный «Текст листа» уезжает вниз. Служебным считается раздел, в заголовке
которого есть: `состав листа`, `из геометрии`, `карта листа`, `описание листа`,
`описание чертежа`, `по изображению`, `якор`. Проверка по образцу, не по точной
формулировке — конвейер её меняет.

Отсюда два следствия для конвейера:

- Дословный текст листа держите в разделе, **не** попадающем под этот образец
  («Текст листа (из чертежа, дословно)» — подходит).
- Отладочное (слои, длины, карта листа) выносите в отдельный `##` — тогда оно не
  мешает чтению, но остаётся доступным по клику.

## Как называется лист в замечаниях и выгрузке

Один формат на таблицу замечаний, подсветку и Excel (`lib/sheet-label.ts`):

| Что видно | Когда |
| --- | --- |
| `лист 28` | всегда; 28 — номер листа тома, он же номер страницы PDF |
| `лист 28 (в штампе 6)` | если конвейер прислал номер из графы «Лист» штампа |

Почему так: в томе ИОС4 инженеры и проектировщики называют лист по порядку в
томе («лист 28»), а в графе «Лист» штампа того же листа стоит 6. Одно число в
замечании без пояснения читается как ошибка, поэтому основным остаётся номер
тома, а штамп идёт справкой в скобках.

Что нужно от конвейера — необязательное поле места, номер строкой:

```json
{ "documentName": "ИОС4-том.pdf", "pageNumber": 28, "stampSheet": "6", "quote": "118 кВт" }
```

Принимаются также имена `sheetNumber` и `stampNumber`. Адрес листа **в самой
формулировке** не нужен: PTO срезает начальные «файл.pdf, стр. N:» и «лист 6,
стр. 1:» и в таблице, и в выгрузке, чтобы номера не спорили между собой.

### Цитата из расшифровки

Цитату со скана конвейер берёт из markdown описания модели, а там числа
выделены: `принята **250 кВт**, а по расчёту нагрузок _180 кВт_`. Чистить её не
нужно — подсветка не замечает `*`, `_`, `` ` ``, `~` ни в цитате, ни в тексте
листа и находит фразу, даже когда разметка рвёт её на части
(`lib/highlight-text.tsx`). Служебный раздел, в котором нашлась цитата,
раскрывается сам — свёрнутым он был бы «совпадения нет».

## Оси цвета в интерфейсе

Осей четыре, и цвета между ними не смешиваются. Любая новая плашка должна
выбрать одну ось. Закреплено сторожем `scripts/palette-check.mjs`.

**Ось 1 — подсветка на чертеже** (`ui-chrome.tsx`, `HighlightLegend`). Не менять:
коллеги её выучили.

| Цвет | Смысл |
| --- | --- |
| зелёная рамка | зона, где искать замечание |
| оранжевая заливка | само значение из замечания |
| синяя заливка | другие места того же замечания |

**Ось 2 — состояние системы**: как идёт обработка файла и листа, плюс
предупреждения конвейера. Только токенами `--sem-*` из `globals.css`, прямые
цвета Tailwind здесь запрещены. Ровно три смысла плюс `--accent` на ход работы и
на всю навигацию.

| Токен | Смысл | Где |
| --- | --- | --- |
| `--sem-attn` | ждёт, требует внимания, режим MOCK | `STATUS_CLASS.queued`, точка «лист правили», плашка про пароль |
| `--sem-ok` | готово | `STATUS_CLASS.done`, точка «текст готов» |
| `--sem-issue` | ошибка, есть отметка | `STATUS_CLASS.error`, `page-reviews-bar`, ошибка листа |

**Ось 3 — важность замечания** (`SEVERITY_CHIP` в `review-colors.ts`). Шкала
инженера: насколько замечание существенно. Значения с цветом различаются
оттенком, иначе в выпадашке они сливаются в одно пятно.

| Значение | Цвет |
| --- | --- |
| `high` | rose |
| `medium` | amber |
| `low` | sky |
| `unset` | белый с пунктирной рамкой |
| `skip` | нейтральный, зачёркнуто |

**Ось 4 — итог разбора** (`VERDICT_CHIP`, `VERDICT_DOT` в `review-colors.ts`).
Независимая от важности шкала: что решили по замечанию. `partial` и `discuss`
стоят рядом в выпадашке, поэтому их различает и оттенок, и форма — у `discuss`
кружок с прорезью внутри (`VERDICT_DOT_INNER`).

| Значение | Цвет |
| --- | --- |
| `confirmed` | emerald |
| `partial` | violet |
| `discuss` | amber, кружок с прорезью |
| `wrong` | rose |
| `pending`, `outdated` | нейтральный |

Строка таблицы замечаний **белая**. Важность красит только клетку «Замечание»:
блеклая заливка и яркая рамка — `high` rose, `medium` amber, `low` sky
(`SEVERITY_REMARK`). Итог разбора фоном строки не передаётся (`VERDICT_ROW`
пуст): он читается подписью и кружком.

## Зоны левой колонки

Левая колонка разбита на зоны сверху вниз: проекты, листы, «Разобрано» внизу.
Каждая отделена **толстой** цветной рамкой: проекты — `border-b-2 border-sky-500`,
«Листы» — `border-t-2 border-emerald-600` (в отдельной панели `border-r-2`, шапка
`border-b-2`), «Разобрано» — `border-t-2 border-amber-500`. Это не украшение:
зоны сделали такими нарочно, чтобы инженер не кликнул мимо нужной. Истончать
эти рамки до 1px нельзя, даже приводя хром к одной толщине — остальные рамки
интерфейса 1px, а разделители зон остаются 2px. Закреплено сторожем
`scripts/palette-check.mjs`.

## Подсветка: связь расшифровки с чертежом

Режим «Подсветка» во фронтенде связывает абзац markdown с подписью на чертеже.
Связь строится в два этапа:

1. **По object ID** (предпочтительно) — если ID совпадает в markdown и геометрии.
2. **По тексту** (fallback) — нечёткое сопоставление нормализованных строк;
   менее точно, возможны пропуски на плотных листах.

### Markdown: ID объекта

Перед абзацем (на отдельной строке или в начале блока):

```markdown
<!-- obj:A1B2C3 -->
Колодец К-4 — сливной колодец с умывальной решёткой
```

| Правило | Значение |
| --- | --- |
| Формат | `<!-- obj:HANDLE -->`, без пробелов в HANDLE |
| HANDLE | стабильный ID объекта DWG (handle / entity id из конвейера) |
| Видимость | комментарий не рендерится, инженер видит только текст абзаца |
| Один ID | один абзац ↔ одна подпись на чертеже |

Пример листа с несколькими привязками:

```markdown
## Страница 3

# План сетей

<!-- obj:7F3A -->
Колодец К-4

<!-- obj:7F3B -->
Труба Ду 200, L=12 м
```

### CSV-геометрия: колонка `id`

У строк `type=text` в CSV геометрии листа добавьте колонку `id` (после `width`
или в заголовке с именем `id` — парсер ищет по имени колонки):

```
# bbox=167.7,-179.4,797.3,265.8; units=mm; scale=1:40
type,layer,color,lw,geom,text,size,rot,anchor,valign,width,id
text,,#000000,,301.3 236.3,Колодец К-4,5.0,,center,middle,40.0,7F3A
```

Значение `id` должно **совпадать** с HANDLE в `<!-- obj:7F3A -->`.

### Ограничения

| Ситуация | Поведение |
| --- | --- |
| `kind: table` | лист ренерится одним блоком — подсветка по абзацам **не работает** |
| PDF (не DWG) | object ID из геометрии нет; только текстовое сопоставление по pdf.js |
| Нет ID в markdown или CSV | fallback по тексту; мелкие подписи могут не связаться |
| Служебные блоки | «карта листа», «якоря», штамп — исключены из привязки |

## Геометрия DWG (для отрисовки и подсветки)

Фронтенд запрашивает CSV геометрии через прокси PTO (не напрямую к конвейеру):

```
GET /api/documents/<documentId>/pages/<pageNumber>/geometry
```

Ответ: `text/csv; charset=utf-8`. Только для листов из DWG/DXF; для PDF — `404`
(чертёж рисует pdf.js).

На стороне конвейера тот же ресурс:

```
GET /jobs/<jobId>/pages/<n>/geometry
```

Минимальный формат CSV:

```
# bbox=x0,y0,x1,y1; units=mm; scale=1:40
type,layer,color,lw,geom,text,size,rot,anchor,valign,width,id
line,СЕТИ,#000000,0.25,100 200 300 200,,,,,,
text,,#000000,,301.3 236.3,Подпись,5.0,,left,baseline,80.0,H001
```

| Колонка | Назначение |
| --- | --- |
| `type` | `line` \| `polyline` \| `text` |
| `geom` | координаты через пробел; у текста — точка вставки `x y` |
| `text`, `size`, `anchor`, `valign`, `width` | только у `type=text` |
| `id` | *(опционально)* object ID для подсветки — см. выше |

Ось Y в чертеже направлена **вверх**; координаты в мм листа. Полное описание
колонок и переносов `\\n` в подписях — в [`docs/dwg-geometry.md`](dwg-geometry.md).

## Проверка глазами

Экран `/reference` в приложении: слева вставляете эталонный `*.ref.md`, справа
подгружаете наш лист по `id` документа и номеру листа. Рендер один и тот же
компонент, что и в рабочем экране, поэтому расхождение видно сразу. Плашки под
текстовым полем показывают, какие элементы контракта найдены.

## Что PTO делает сам

- Хранит PDF и отдаёт постранично для просмотра.
- Классифицирует листы эвристикой (`source: heuristic`), пока не пришёл ваш
  результат. Ваш `PUT` заменяет лист и меняет бейдж источника на «Модель».
- Ведёт замечания инженеров с привязкой к месту на чертеже и журнал правок.
