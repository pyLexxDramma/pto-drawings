# Контракт замечаний: как отдавать найденные расхождения в PTO

Документ для команды конвейера. PTO показывает чертёж и расшифровку, а поверх
них ведёт таблицу замечаний по проекту: раздел, формулировка, место в ПД,
важность. Инженер размечает важность и итог разбора с заказчиком, затем
выгружает XLSX для отправки проектировщикам.

Контракт листа — в [`page-contract.md`](page-contract.md), геометрия DWG — в
[`dwg-geometry.md`](dwg-geometry.md).

## Запрос

```
PUT /api/projects/<projectId>/reviews
Authorization: Bearer <PTO_INGEST_TOKEN>
Content-Type: application/json
```

`projectId` и `documentId` — те же значения, что PTO присылает конвейеру в
`POST /jobs` (`projectId` и `documentId` в теле запроса). Отдельной ручки поиска
не нужно: возвращайте их как получили.

Тело — пачка замечаний целиком, за один вызов:

```json
{
  "reviews": [
    {
      "section": "ПБ",
      "origin": "ai",
      "text": "",
      "aiFinding": "Объём пожарного резервуара расходится: расчёт ПБ — 310 м³, экспликация — 250 м³. Должна быть единая цифра.",
      "severity": "high",
      "locations": [
        {
          "documentId": "6f4774cb-471e-4fe6-889d-644da8657295",
          "documentName": "Раздел ПД №9 (ПБ)",
          "pageNumber": 919,
          "quote": "К установке принимаем 2 резервуара, объёмом 310 м³ каждый",
          "rect": { "x": 0.12, "y": 0.34, "w": 0.18, "h": 0.04 }
        },
        {
          "documentId": "6f4774cb-471e-4fe6-889d-644da8657295",
          "documentName": "Раздел ПД №9 (ПБ)",
          "pageNumber": 4089,
          "quote": "250 м³"
        }
      ]
    }
  ]
}
```

| Поле | Обязательное | Значения | Что делает |
| --- | --- | --- | --- |
| `section` | да | любая строка, см. «Разделы» ниже | группирует таблицу |
| `aiFinding` | для новых находок — да; для обогащения по `reviewId` — нет | строка | обоснование от конвейера |
| `reviewId` | нет | uuid строки в PTO | обновить эту строку, не искать по тексту |
| `needsRecheck` | нет | `true` / `false` | цитату не нашли или агент не уверен |
| `text` | нет | строка | формулировка инженера, если она уже известна |
| `severity` | нет | `high`, `medium`, `low`, `skip`, `unset` | находка ИИ без поля — `medium`; ручная отметка — `unset` («Не задана»). `skip` и `unset` не попадают в выгрузку |
| `origin` | нет | `ai`, `engineer` | по умолчанию `ai`; `both` не присылайте — PTO ставит его сам |
| `locations` | нет | массив, см. ниже | место в ПД; расхождение задаётся двумя элементами |

Локация:

| Поле | Обязательное | Что значит |
| --- | --- | --- |
| `documentId` | нет | id файла в PTO; `null` для замечаний уровня `межраздел` |
| `documentName` | да | как называть раздел в выгрузке: «Раздел ПД №9 (ПБ)» |
| `pageNumber` | нет | страница PDF (не «лист ГЧ») |
| `quote` | нет | цитата из ПД — по ней проверяющий находит место за секунды |
| `rect` | нет | рамка на листе, доли 0..1: `{ "x", "y", "w", "h" }`. Также принимаем `bbox` как `{x0,y0,x1,y1}` или `[x0,y0,x1,y1]`. Пиксели (>1) игнорируются. |

`quote` теперь работает и в расшифровке: если цитата встречается в тексте листа,
PTO подсвечивает это место, а в списке листов у файла появляется счётчик
замечаний. Чем точнее цитата совпадает с текстом расшифровки, тем меньше
инженер ищет глазами.

Ответ `200`:

```json
{ "added": 128, "updated": 34, "enriched": 6, "total": 162 }
```

`enriched` — сколько находок прицепилось к замечаниям, которые инженер завёл
руками (см. ниже).

`PUT` **не удаляет** устаревшие строки. Повторный прогон без штампа `10/28`
не снимет вчерашнюю строку — она останется и фронт будет зумить в первое «10».
Снять брак конвейера:

```
DELETE /api/projects/<projectId>/reviews/<reviewId>
Authorization: Bearer <PTO_INGEST_TOKEN>
```

Только `origin: ai`. Строки инженера и `both` токен не трогает. `403` — чужое,
`404` — нет такой строки.

Коды ошибок: `401` — неверный токен, `404` — нет такого проекта, `400` —
не массив `reviews` или неизвестная важность, `503` — на сервере не задан
`PTO_INGEST_TOKEN`.

## Идемпотентность: чем это важнее, чем кажется

Ключ замечания — `section` + `aiFinding` + список мест (имя раздела и
страница). Повторный `PUT` того же замечания **обновляет** его, а не добавляет
второе.

Разбор замечаний с заказчиком идёт построчно и занимает часы, поэтому при
обновлении сохраняется всё, что проставил человек:

- `verdict` (итог разбора: `pending`, `confirmed`, `partial`, `discuss`,
  `outdated`, `wrong`) не трогается никогда и в приёме не участвует — его
  ставит человек;
- `comment` и `wrongReason` не трогаются никогда;
- `severity` перезаписывается только пока `verdict` = `pending`; после разбора
  важность, выставленную человеком, конвейер не меняет;
- `text` и `locations` уточняются, если в запросе они непустые;
- если замечание пришло от инженера, а потом его подтвердил конвейер, `origin`
  становится `both` — в таблице это «Клиент + ИИ».

Из этого следует: **менять формулировку `aiFinding` между прогонами нельзя**,
иначе замечание считается новым и разбор по нему потеряется. Если формулировку
надо поправить, лучше прислать её в `text`.

## Замечания, заведённые руками

Инженер часто заводит замечание раньше конвейера и без пути в ПД: «диаметр
стояка К1 не сходится с аксонометрией». Когда агент находит то же самое, PTO не
создаёт дубль, а дописывает такому замечанию `aiFinding` и `locations` — то есть
файл, страницу и цитату, — и помечает строку как «Совпало» (`origin: "both"`).

Ищется это по совпадению значимых слов формулировок **внутри одного раздела**:
слова режутся до основы (падежи иначе не совпадают), слова короче четырёх букв
отбрасываются, но числа и шифры остаются целиком — `310`, `К1`, `ОВ1`, `42.5`
как раз точнее всего показывают, что речь об одном и том же. Нужно не меньше
трёх общих элементов при перекрытии от 70%. Порог намеренно высокий: лучше
лишний раз не склеить, чем склеить разное. Одна находка цепляется максимум к
одному ручному замечанию.

Отсюда практическое следствие: чем ближе `aiFinding` к тому, как формулирует
инженер, тем чаще срабатывает склейка. Формулировку инженера агент при этом не
перебивает — она остаётся в `text` и попадает в выгрузку.

## Разделы: список не закрытый

`section` — произвольная строка. Порядок в таблице и выгрузке такой:

1. разделы ПД составом комплекта: `ПЗ`, `ПЗУ`, `АР1`–`АР5`, `КР1`–`КР4`,
   `ИОС1`–`ИОС5`, `ПОС`, `ПБ`, `ТБЭ`, `ОДИ`;
2. марки рабочей документации: `АР`, `КЖ`, `КМ`, `ТХ`, `ОВ`, `ВК`, `ТС`, `ЭО`,
   `ВН`, `НВ`, `НК`, `НЭС`, `НСС`, `АПС`, `АПТ`, `СОУЭ`, `ДУ`, `АСДУ`, `СКУД`,
   `СС`, `СОТС`;
3. всё остальное — по порядку первого появления. Полный шифр тома вида
   `250910-ВА-Р-ОВ1` присылать можно: такие разделы идут группами в том порядке,
   в котором пришли, и в конец одной кучей не сваливаются;
4. `межраздел` — всегда последним.

Регистр и лишние пробелы не важны. Одному разделу — одна строка написания:
`ОВ` и `250910-ВА-Р-ОВ1` для PTO разные разделы, поэтому выберите один способ и
держитесь его в пределах проекта.

Договорились так: конвейер присылает **полный шифр тома из штампа**, одним
написанием на весь проект. PTO это принимает без списка — такие разделы идут
группами в порядке появления. Единственное, что от этого зависит: склейка с
ручными замечаниями ищется **внутри одного раздела**, поэтому если по одному и
тому же тому в разных пачках приедут `ОВ` и `250910-ВА-Р-ОВ1`, находка к
замечанию инженера не прицепится.

## Потоки: `origin` виден в интерфейсе

Над таблицей фильтр «Нашла ИИ / Инженер / ИИ и инженер», и у каждой строки есть
метка потока. На разборе с заказчиком видно, где находка конвейера, а где
формулировка инженера.

- `ai` — находка конвейера.
- `engineer` — человек: Excel или кнопка «Отметить ошибку» на чертеже/в тексте.
- `both` — PTO ставит сам при склейке («ИИ и инженер»). Присылать не надо.

## Ручная отметка на чертеже (0063, 0072)

«Отметить ошибку» сразу пишет строку в таблицу замечаний (`origin: engineer`),
с файлом, номером листа и текстом «что не так / должно быть». Счётчик меняется
тут же, без ожидания ИИ. Рамку на чертеже PTO хранит как аннотацию. Обогащение
координатами/разделом — отдельный шаг агента, не блокирует появление строки.

### Откуда берётся важность (0072)

Это не оценка ИИ и не правило проверки. Фронт при ручной отметке **не шлёт**
`severity`: `POST /api/documents/<id>/annotations` вызывает `createReview` с
`origin: "engineer"` без важности, и PTO ставит `unset` («Не задана»). Раньше
здесь был жёсткий дефолт `medium` («Средний») — инженер видел заполненное поле
и думал, что система что-то оценила.

Находка конвейера (`PUT /reviews`, `origin: ai`): важность берётся из пачки.
Если конвейер поле не прислал — дефолт `medium`. ИИ может прислать `high` /
`medium` / `low` / `skip` по своему правилу; фронт это не пересчитывает.

Excel-импорт инженера без колонки важности — тоже `unset`.

### Что заполняется само, что руками

При ручной отметке PTO сам пишет только:

- `origin: engineer`
- `verdict: pending`
- `text` из «что не так» (+ «Должно быть», если заполнено)
- одна локация: `documentId`, `documentName`, `pageNumber`, `quote` = комментарий
- рамку на листе — в аннотации, не в `locations[].rect`

Не заполняются: `section` (становится `прочее`), `aiFinding`, `locations[].rect`,
`locations[].quote` из текста ПД, важность, итог разбора. Раздел, цитата из ПД
и рамка в таблице появятся после обогащения агентом или руками. Важность
инженер ставит сам — без неё строка в XLSX проектировщикам не идёт (0062).

## Что делает PTO дальше

Приём замечаний зажигает второй этап в полосе прогресса проекта: «Расшифровка →
Замечания». Этап считает, сколько замечаний разобрано с заказчиком
(`verdict` ≠ `pending`) из общего числа, и пока пачка не пришла, остаётся серым.
Так что первый успешный `PUT` по проекту сразу видно всей команде.

Замечание с `verdict: "wrong"` — это брак находки: инженер обязан написать, что
именно неверно (`wrongReason`), и такая строка в выгрузку проектировщикам не
идёт. Это и есть обратная связь конвейеру: в шапке таблицы виден счётчик
«брак ИИ N», а причины можно собрать из `wrongReason` по проекту. Туда же не
попадают `verdict: "outdated"` (снято на разборе), `severity: "skip"`
и `severity: "unset"` (важность ещё не выбрана).

Все правки строк пишутся в журнал (`events` в файле проекта): поле, было/стало,
кто и когда. Журнал отдаётся вместе с таблицей в `GET` и виден по кнопке в
строке — на разборе всегда можно ответить, кто снял замечание.

Порядок в таблице и в выгрузке: сначала раздел в порядке комплекта ПД, внутри
раздела — важность сверху вниз (`unset` → `high` → `medium` → `low`), при равной важности
по дате. Номера `№` пересчитываются автоматически, присылать их не нужно.

Таблица — плоский список, как Excel. Группировку «по разделам / по файлам»
убрали, пока разделы с конвейера кривые. `documentName` всё равно стоит
присылать одной строкой на файл: от него зависят колонка «Где в ПД» и фильтр.

Выгрузка `GET /api/projects/<projectId>/reviews/export` отдаёт XLSX в формате
официальной отправки проектировщикам: `№ · Раздел · Замечание · Где в ПД`.
Строки покрашены по важности, `skip` и `unset` в файл не попадают. В колонку «Замечание»
идёт `text`, а если он пуст — `aiFinding`.

## Остальные маршруты (для интерфейса, не для конвейера)

| Маршрут | Назначение |
| --- | --- |
| `GET /api/projects/<id>/reviews` | список для таблицы |
| `POST /api/projects/<id>/reviews` | замечание руками: инженер или клиент |
| `PATCH /api/projects/<id>/reviews/<reviewId>` | важность, итог разбора, комментарий |
| `DELETE /api/projects/<id>/reviews/<reviewId>` | удалить замечание (сессия или токен ингеста для `origin: ai`) |
| `GET /api/projects/<id>/reviews/export` | XLSX |
| `POST /api/projects/<id>/reviews/import` | Excel/CSV инженера → поток `engineer` |
| `POST /api/projects/<id>/reviews/enrich` | прокси к агенту: `POST {PTO_BACKEND_URL}/reviews/enrich` |

Импорт и выгрузка работают по сессии. Обогащение зовёт конвейер — без ручки агента фронт отвечает `501`.

## Обогащение замечаний инженера (нужна новая ручка)

Инженер грузит свой Excel. Строки попадают в таблицу как `origin: "engineer"`:
формулировка как есть, раздел часто `прочее`, мест в ПД нет. Кнопка «Обогатить»
шлёт агенту только эти строки (и те, где `needsRecheck: true`).

```
POST {PTO_BACKEND_URL}/reviews/enrich
Content-Type: application/json
```

Вход:

```json
{
  "projectId": "тот же, что в POST /jobs",
  "reviews": [
    { "id": "uuid-строки-в-PTO", "text": "Диаметр ВСХ-20 не сходится", "section": "прочее" }
  ]
}
```

Выход — тот же формат, что принимает `ingestReviews` (`PUT /reviews`):

```json
{
  "reviews": [
    {
      "reviewId": "uuid-строки-в-PTO",
      "section": "ОВ",
      "aiFinding": "Диаметр ВСХ-20 на плане не сходится со спецификацией",
      "locations": [
        {
          "documentId": "id файла из POST /jobs",
          "documentName": "250910-ВА-Р-ОВ1",
          "pageNumber": 12,
          "quote": "ВСХ-20"
        }
      ],
      "needsRecheck": false,
      "origin": "ai"
    }
  ]
}
```

Правила:

- `reviewId` = входной `id`. Без него PTO будет искать склейку по словам и может
  промахнуться.
- `text` инженера **не переписывать**. Свою формулировку класть в `aiFinding`.
- `quote` — точная подстрока текстового слоя листа (как в расшифровке). По ней
  фронт подсвечивает место на чертеже. Пересказ своими словами подсветку ломает.
- `documentId` / `pageNumber` — те же, что конвейер уже знает по этому проекту.
- `needsRecheck: true`, если цитату не нашли или уверенность низкая. Тогда
  `locations` можно оставить пустыми.
- Идемпотентно по `reviewId`: повторный вызов обновляет ту же строку.
- Вызывать только когда расшифровка проекта `done`. Если листы ещё считаются —
  ответить ошибкой, не пустым успехом.
- Не плодить новые строки: это не слой поиска расхождений (`PUT /reviews`),
  а дописывание уже существующих.
- Таймаут на стороне PTO — 120 с. Если дольше — лучше сразу `202` с понятной
  ошибкой «ещё считается», чем молча оборвать сокет.

`PTO_AUTO_PUBLISH` / слой 2 (свои находки ИИ через `PUT /reviews`) от этого
не зависит и по-прежнему нужен отдельно.

## Проверить руками

```bash
curl -X PUT "https://pto.tw1.su/api/projects/$PROJECT/reviews" \
  -H "Authorization: Bearer $PTO_INGEST_TOKEN" \
  -H "Content-Type: application/json" \
  --data @reviews.json
```

Проверка токена без данных: `PUT` в несуществующий проект должен ответить `404`.
`401` означает, что токен не тот, `503` — что на фронте он не задан.

## Окружение конвейера на нашем проде

В `/opt/pto/backend/.env` уже прописано (08.09), контейнер пересоздан:

```
PTO_FRONT_URL=https://pto.tw1.su
PTO_INGEST_TOKEN=<тот же, что у интерфейса>
PTO_AUTO_PUBLISH=1
```

Адрес внешний, а не `http://frontend:8080`: на этом сервере интерфейс не в
compose — он поднят как systemd-юнит `pto` в `/var/www/pto`, поэтому из
контейнера имя `frontend` не резолвится, а шлюз docker-сети (`172.18.0.1:8080`)
закрыт файрволом. Внешний адрес из контейнера проверен — отвечает `200`.
